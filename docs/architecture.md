# Устройство приложения

## Общая схема

```
┌──────────────── ПК (хаб) ─────────────────┐        ┌──── Телефон ─────┐
│  Node + Fastify, один процесс             │        │                  │
│                                           │        │  Браузер / PWA   │
│   /api/*          HTTPS: файлы и текст    │◄─ LAN ─┤  открыт по QR    │
│   /api/events     WebSocket: уведомления  │  Wi-Fi │  «Поделиться»    │
│   /                статика (src/web)      │        └──────────────────┘
│                                           │
│   ~/LanSync/inbox        файлы            │        ┌──── Ноутбук ─────┐
│   ~/LanSync/.thumbs      миниатюры        │◄───────┤  тот же интерфейс│
│   ~/LanSync/clips.json   история текста   │        └──────────────────┘
│   ~/LanSync/devices.json привязки         │
│   ~/LanSync/tls/         сертификат       │
│   ~/LanSync/config.json  общий токен      │
└───────────────────────────────────────────┘
        ▲
        └── тот же интерфейс на localhost
```

Топология — «ПК как хаб»: сервис живёт на одном компьютере, остальные устройства
подключаются к нему. Полноценный P2P (каждое устройство и клиент, и сервер) потребовал бы
нативных приложений на всех платформах; при выбранной схеме мобильный клиент — обычная
веб-страница, которую не нужно устанавливать и обновлять.

Плата за это: если компьютер выключен или спит, обмен недоступен.

**Между двумя компьютерами это возражение не действует**, и там связь прямая. Довод против
P2P был про телефон, который не может держать сервер; компьютер с LanSync его уже держит,
клиент писать не нужно — оба конца одинаковые. Поэтому ПК находят друг друга по mDNS, а
отправка идёт напрямую: отправитель обращается к тому же `POST /api/files`, каким пользуется
браузер, со своим персональным токеном. Ничего похожего на синхронизацию папок здесь нет —
это то же разовое «отправить», только инициируемое не человеком у чужой страницы, а
компьютером-отправителем. Подробности — в разделе «Соседние компьютеры».

## Почему так

**Мобильный клиент — браузер, а не нативное приложение.** Работает на iOS и Android
одинаково и сразу, без сборки, подписи и магазинов приложений.

**Фронтенд без сборщика.** `src/web` — обычные HTML, CSS и ES-модули, которые отдаются как
есть. Нет ни шага сборки, ни source maps, ни рассинхрона между исходником и тем, что
выполняется в браузере. Правка видна после обновления страницы.

**Стриминг вместо буферизации.** Загружаемый файл идёт `part.file → createWriteStream`
через `pipeline`, скачиваемый — `createReadStream`, архив — прямо в сокет. Ни при отправке,
ни при приёме файл не собирается в памяти, поэтому размер ограничен только диском.

**Список файлов не индексируется.** `GET /api/files` каждый раз читает каталог. Это
медленнее индекса, но исключает рассинхрон и позволяет класть файлы в каталог обмена мимо
приложения — они сразу видны. При тысячах файлов имеет смысл вернуться к этому решению.

## HTTPS и самоподписанный сертификат

Приложение работает по HTTPS не ради шифрования как такового: браузеры считают защищённым
контекстом только HTTPS и `localhost`, а без защищённого контекста недоступны
`navigator.clipboard`, service worker (офлайн-режим) и Web Share Target. То есть половина
возможностей приложения существует лишь потому, что соединение защищено.

`tls.ts` создаёт сертификат при первом запуске и складывает в `~/LanSync/tls/`. Ключевая
деталь — **subjectAltName**: браузер принимает сертификат только если запрошенный адрес
перечислен в SAN. Поэтому сертификат выписывается на все текущие адреса машины плюс
`localhost`, `127.0.0.1` и имя хоста, а рядом сохраняется список этих имён. При следующем
запуске список сверяется с актуальным, и если машина сменила адрес — сертификат
перевыпускается автоматически. Срок — 10 лет, чтобы истечение никогда не стало сюрпризом.

Предупреждение браузера при первом заходе неизбежно: доверенный сертификат на приватный
IP-адрес не выдаёт ни один центр сертификации.

На соседнем порту (`8421`) поднимается крохотный HTTP-сервер, который только перенаправляет
на HTTPS — для случая, когда адрес набирают руками. Через брандмауэр он по умолчанию не
пропущен, так что с телефона обычно недоступен; это осознанно, редирект нужен в первую
очередь на самом компьютере.

## Поток данных

**Отправка файла.** Браузер шлёт `multipart/form-data` через `XMLHttpRequest` — он, в отличие
от `fetch`, сообщает прогресс отправки. Сервер санитизирует имя, разводит коллизии суффиксом
и пишет поток на диск. После записи `EventHub.broadcast('file:added')` рассылает событие всем
подписчикам, и остальные устройства перерисовывают список сами.

Каждый файл уходит отдельным запросом, по три одновременно. Раньше вся выборка отправлялась
одним запросом, и при превышении лимита в 50 файлов сервер отвечал `413` на всю пачку —
хотя 50 файлов к тому моменту уже лежали на диске. Пользователь видел ошибку, а файлы были на
месте. Теперь у каждого файла свой прогресс, своя отмена и своя кнопка «Повторить», а порога
на число файлов нет вовсе. Серверный обработчик всё равно сообщает, что именно принято, если
пачку оборвало на середине — молчаливая потеря недопустима.

**Скачивание.** Ручная обработка `Range` вместо готового статик-плагина: нужен код `206` и
заголовок `Content-Range`, иначе на телефоне не перематывается видео. Имя отдаётся по RFC 6266
с ASCII-запасным вариантом и `filename*=UTF-8''…`, чтобы не терять кириллицу.

**Архив.** `archiver` собирает ZIP на лету и пишет прямо в ответ — временного файла нет,
поэтому размер выборки ограничен только диском получателя. Сжатие выключено: внутри почти
всегда уже сжатые фото и видео, а нулевой уровень заметно ускоряет отдачу. Суммарный размер
известен заранее из листинга, и при превышении 4 ГБ включается ZIP64 — иначе обычный ZIP
не сможет адресовать данные.

**Уведомления.** `EventHub` держит множество подписчиков; роуты дёргают `broadcast` после
каждой мутации. Поллинга нет.

## Доступ и устройства

Общий токен генерируется при первом запуске и лежит в `~/LanSync/config.json`. Он вшит в
ссылку QR-кода, поэтому вручную его обычно не вводят.

Общий токен работает как **код привязки**: отсканировав QR, страница сразу вызывает
`POST /api/pair` и обменивает его на персональный токен устройства. Записи хранятся в
`devices.json` вместе с именем (выводится из `User-Agent`), адресом и временем последней
активности. Смысл этой прослойки один: отозвать одно устройство, не отключая остальные.
С единственным общим секретом потерянный телефон можно было бы отвязать только сменой
токена, то есть переподключением всех.

Проверка (`src/server/auth.ts`) принимает три варианта:

- запрос с самой машины (`127.0.0.1`, `::1`) — иначе пользователю пришлось бы копировать
  секрет в собственный браузер;
- персональный токен устройства;
- общий токен — остаётся рабочим и удобен для скриптов.

Своим считается именно loopback, а не машина целиком: браузер на ПК, открывший страницу по
сетевому адресу этой же машины, приходит с сетевого адреса и от телефона по источнику
неотличим. Расширять проверку на все адреса машины не стали — на разнице loopback и LAN
держится вся проверка доступа против живого сервера (`scripts/smoke.mjs`). Вместо этого
`app.ts` перенаправляет такой запрос страницы на `localhost`; ссылку с токеном (`?t=`)
перенаправление пропускает — по ней вид телефона смотрят с ПК нарочно.

Эндпоинты `/api/connect`, `/api/token/rotate` и `DELETE /api/devices/:id` доступны **только
локально**: иначе устройство без доступа смогло бы запросить сам токен, а любое привязанное —
отвязать остальные.

Сравнение токенов — `timingSafeEqual`. Без токена любой в той же сети — включая гостевой
Wi-Fi в кафе — читал бы и писал ваши файлы.

**Три способа разорвать доступ.** «Отключиться» на телефоне стирает токен из `localStorage`.
«Отвязать» на компьютере удаляет запись устройства и рвёт его подписки (код `4003`).
«Отключить все устройства» меняет общий токен, очищает реестр и рвёт все подписки (код `4001`).

## Соседние компьютеры

Два ПК с LanSync находят друг друга по mDNS (`src/server/peers.ts`): каждый анонсирует службу
`lansync` с TXT-записью, где лежат идентификатор машины, имя, признак TLS и отпечаток
сертификата. Собственный анонс отсеивается **по идентификатору**, а не по адресу: два
экземпляра на одной машине — штатный способ проверки, и адрес у них общий. Идентификатор
постоянный, лежит в `config.json` рядом с общим токеном и переживает смену токена.

Рассылку mDNS в чужих сетях часто режут, поэтому соседа всегда можно добавить вручную по
адресу — обнаружение только избавляет от этого в обычном случае.

**Привязка.** Принимающая сторона показывает шестизначный код (в памяти, 5 минут, гаснет
после первого удачного обмена или пяти промахов). Отправитель предъявляет его на
`POST /api/peers/adopt` — единственном эндпоинте без токена, кроме `/api/info`, — и получает
персональный токен. Дальше он для соседа обычное устройство: видно в общем списке и
отзывается той же кнопкой «Отвязать», что и телефон. Второго механизма доступа не заводилось.

Ключи от соседей хранит **отправитель** (`peers.json`). Привязка односторонняя: чтобы слать
в обе стороны, код показывают по очереди на каждой машине.

**Доверие сертификату.** Центра сертификации нет, поэтому работает TOFU: отпечаток соседа
запоминается при привязке и сверяется на каждом соединении. Просто отключить проверку было
нельзя — тогда отвечать под нужным адресом смог бы кто угодно в сети, и мы отправили бы ему
файлы вместе с токеном. Проверка идёт **до** создания запроса (`connectVerified` в
`peer-client.ts`): у HTTPS-запроса событие `socket` приходит уже после рукопожатия, и внутри
него отказываться поздно — заголовок с токеном успел бы уйти.

Сертификат соседа законно перевыпускается при смене набора его адресов, то есть отпечаток
меняется и без всякой подмены. Отличить одно от другого нельзя, поэтому сосед помечается
`changedFingerprint`, отправка ему закрывается, а решение принимает человек.

**Отправка.** Тело `multipart/form-data` собирается вручную поверх `node:https` со стримом
с диска: `fetch` с `FormData` буферизует форму целиком (см. `docs/pitfalls.md`). Очередь —
три передачи одновременно, как у страницы; ход отправки уходит событием `peer:progress`.

## Живучесть соединения

Само подключение устройства бессрочно: токен лежит в `localStorage` и переживает
перезагрузку телефона и закрытие браузера. Ограничения по времени нет — доступ снимается
только вручную.

Поток событий восстанавливается сам:

- клиент переподключается с экспоненциальной задержкой, растущей до 15 секунд;
- при возврате вкладки из фона (`visibilitychange`) соединение проверяется сразу, не дожидаясь
  таймера — иначе после разблокировки телефона список молча не обновлялся бы;
- сервер раз в 30 секунд шлёт ping и разрывает соединение, если не пришёл pong. Телефон,
  ушедший из зоны Wi-Fi, не всегда присылает `close`, и без пингов сокет остался бы
  «наполовину открытым», занимая подписку. Ответы на ping заодно обновляют `lastSeen`
  устройства.

Зелёная точка в шапке означает живое соединение, красная — идёт переподключение.

## Миниатюры

Превью строит **отправитель**: браузер уже держит выбранную картинку распакованной, поэтому
уменьшить её до 256×256 через `createImageBitmap` и `canvas` почти ничего не стоит. Готовый
JPEG уходит вместе с файлом в поле `thumb`, сервер просто кладёт его в кэш.

Это решение выбрано не ради экономии процессора, а ради поставки: единственная нативная
зависимость (`sharp`) не упаковывается в самодостаточный исполняемый файл. Перенеся генерацию
в браузер, мы получаем и превью, и один файл без зависимостей.

`sharp` остаётся **необязательным** и используется, когда доступен: он строит превью для
файлов, положенных в каталог обмена мимо приложения. Загружается лениво через `import()` в
`try/catch`, и проверяется именно вызываемость результата — модуль может разрешиться, но не
отдать функцию, и тогда сравнение с `null` пропустило бы неработающий `sharp` как доступный.
Флаг `/api/info.serverThumbs` сообщает только об этой возможности; на отображение он не влияет,
поэтому интерфейс запрашивает превью всегда и подменяет значком по ошибке.

Кэш — `~/LanSync/.thumbs`, ключ — хэш от имени файла и времени изменения, поэтому подменённый
файл получает новую миниатюру без ручной инвалидации. Осиротевшие миниатюры подчищаются при
удалении файлов и при периодическом проходе автоочистки.

Превью только для изображений, которые умеет декодировать браузер: HEIC с iPhone обычно не
поддаётся, и тогда показывается значок. Кадр из видео потребовал бы ffmpeg — несопоставимая по
весу зависимость.

Обратите внимание: самая простая альтернатива (отдать `<img src="/api/files/:id">` и уменьшить
средствами CSS) заставила бы телефон скачать полный размер каждого файла — галерея из пятидесяти
фото вытянула бы сотни мегабайт.

## Поставка одним файлом

Приложение собирается в один исполняемый файл через Node SEA: `esbuild` сводит сервер в один
CJS-модуль, файлы клиента кладутся внутрь как ресурсы SEA, и всё это внедряется в копию
исполняемого файла Node с помощью `postject`. Результат — около 90 МБ, внутри Node, никаких
внешних зависимостей.

Ради этого пришлось убрать две вещи:

- **`clipboardy`** тащил с собой готовые исполняемые файлы (`xsel`, `clipboard.exe`), а их
  нельзя упаковать внутрь. `clipboard.ts` теперь обращается к штатным утилитам системы
  напрямую. В Windows запись идёт через временный UTF-8 файл и `Set-Clipboard`, а не через
  `clip.exe`: тот сохраняет BOM как часть текста и переводит `\n` в `\r\n`, ломая round-trip.
- **`@fastify/static`** требовал каталог на диске, которого в бинарнике нет. `static.ts`
  читает файлы либо с диска (при запуске из исходников — тогда правки видны после обновления
  страницы), либо из ресурсов через `node:sea`. Список отдаваемых путей закрытый, поэтому
  склейки путей из запроса нет вовсе и выход за пределы каталога невозможен.

Две тонкости сборки:

- в формате CJS нет `import.meta`, а он используется для поиска корня проекта — `esbuild`
  подставляет эквивалент на основе `__filename` через `banner` и `define`;
- `useCodeCache` выключен: кэш кода привязан к версии и платформе Node и делает сборку
  непредсказуемой.

Файлы под три ОС собирает CI, каждая платформа на своей системе. Кросс-сборка возможна
технически, но macOS требует переподписи бинарника через `codesign` после внедрения — без
неё Gatekeeper не даёт запустить файл.

## Автозапуск

`autostart.ts` использует штатные механизмы: в Windows — VBScript в папке «Автозагрузка»
(именно скрипт, а не ярлык, чтобы процесс стартовал скрыто и не открывалось окно консоли),
в macOS — LaunchAgent, в Linux — пользовательский юнит systemd. Все три запускают приложение
с флагом `--quiet`.

Автозапуск отказывается прописываться, если приложение запущено из исходников: там нужен ещё
и Node с самим проектом, и ярлык на `node.exe` был бы бесполезен.

## Брандмауэр Windows

Самая частая причина «телефон не видит компьютер». `firewall.ts` умеет проверить наличие
правила, определить категорию текущей сети (от неё зависит профиль правила — офисный Wi-Fi
попадает в `Public`, и правило для `Private` молча не сработает) и создать правило, запросив
повышение прав через UAC. Элевированный PowerShell получает скрипт во временном файле — так не
приходится изобретать вложенное экранирование кавычек.

При обычном запуске сервер проверяет правило и, если его нет, печатает предупреждение с готовой
командой: молча стартовать в состоянии, где телефон не подключится, — худший вариант.

## Автоочистка

`cleanup.ts` раз в час удаляет из каталога обмена файлы старше `LANSYNC_KEEP_DAYS`. Приложение
задумано как перевалочный пункт, а не хранилище, и без этого каталог растёт бесконечно. При
`keepDays: 0` удаление выключено, но проход всё равно выполняется — он подчищает миниатюры,
потерявшие свои файлы.

Первый проход выполняется при старте и доступен как `cleaner.ready`. Это не украшение: без
наблюдаемого промиса тест не мог отличить «уборка не сработала» от «уборка уже прошла в
фоне» — именно на этом он сначала и падал.

## Приём из меню «Поделиться»

`manifest.webmanifest` объявляет Web Share Target на `POST /share`. Запрос перехватывает
service worker, разбирает `multipart/form-data`, раскладывает файлы по `POST /api/files`
(по одному, как это делает страница), текст — в `POST /api/clips`, и перенаправляет на
`/?shared=1`.

Тонкость: у service worker нет доступа к `localStorage`, где лежит токен. Поэтому страница
при загрузке кладёт токен в Cache Storage (`lansync-auth`, ключ `/__token`), откуда worker его
и читает. Серверный обработчик `/share` отвечает редиректом на `/` — он нужен на случай, когда
worker ещё не активен, чтобы вместо ошибки пользователь увидел приложение.

Работает только на Android: iOS не поддерживает Web Share Target.

### Выбор сетевого адреса

Самая неочевидная часть. На типичной машине разработчика несколько адаптеров с приватными
адресами: WSL, Hyper-V, VirtualBox, Docker. Эвристика «взять первый адрес из 192.168.\*»
уверенно выбирает виртуальный адаптер, и QR-код ведёт туда, куда телефон не достучится.

Поэтому основной адрес определяется по таблице маршрутизации: создаётся UDP-сокет и
«подключается» к внешнему адресу. Пакеты не отправляются — `connect` лишь заставляет ядро
выбрать маршрут, после чего локальный адрес сокета и есть искомый. Решение принимает сама
система, а не список эвристик.

Имена интерфейсов используются как запасной путь: адаптеры с `vethernet`, `virtualbox`,
`vmware`, `docker` и подобными в названии понижаются в списке.

## Пределы

| Что | Значение |
|---|---|
| Размер одного файла | практического потолка нет — упирается в диск |
| Файлов за один запрос API | 50 (веб-интерфейс шлёт по одному, порога не видит) |
| Одновременных отправок из интерфейса | 3 |
| Размер архива | не ограничен; свыше 4 ГБ включается ZIP64 |
| Текстовых записей в истории | 50 |
| Длина текстовой записи | 100 000 символов |
| Тайм-аут запроса | отсутствует |

Размер файла ничем не ограничивается искусственно: `limits.fileSize` выставлен в
`Number.MAX_SAFE_INTEGER`, `bodyLimit` Fastify на multipart не распространяется, таймауты
запроса и соединения отключены. Проверено передачей файла на 5 ГБ: он пересекает границы
2 ГБ и 4 ГБ, на которых обычно и ломаются реализации, а память процесса при приёме выросла
с 91 до 148 МБ — то есть файл действительно не собирается в памяти.

Реальные ограничения лежат снаружи:

- **свободное место** в каталоге обмена;
- **файловая система** — на FAT32 или exFAT-флешке потолок 4 ГБ на файл, на NTFS его нет;
- **скорость сети** — по Wi-Fi 5 ГГц реально 20–50 МБ/с, то есть файл на 5 ГБ идёт несколько
  минут.

## Ограничения

**Трафик шифруется, но доверие к сертификату — ручное.** Самоподписанный сертификат защищает
от пассивного прослушивания, но не подтверждает подлинность сервера при первом соединении.

**Нет докачки.** Оборванная передача начинается заново.

**Одновременное редактирование не разрешается.** Файл с совпадающим именем не перезаписывается,
а сохраняется рядом с суффиксом. Это обмен, а не синхронизация папок.

## Тестирование

```bash
npm test
```

Тесты поднимают настоящий сервер на случайном порту и ходят по нему `fetch` (с `tls: false` —
самоподписанный сертификат в тестах только мешает). Проверяются целостность байтов при
загрузке и скачивании, `Range`, санитизация имён, коллизии, работа с текстом, сборка архива,
пакетное удаление, миниатюры и автоочистка.

Авторизация, привязка и отзыв устройств проверяются через `app.inject()` с подменённым
`remoteAddress`: запросы с localhost авторизуются автоматически, поэтому обычным `fetch`
ни отказ в доступе, ни привязку не воспроизвести — нужен адрес «из сети».
